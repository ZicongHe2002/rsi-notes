# 执行后检查只有一个函数，为什么不等于隔离候选代码

自动设计代理可以生成Python函数，再由评估器执行。这里有两种不同问题：输出是否符合“一个可调用入口”的接口约定，以及候选执行时能接触什么状态。入口检查不能自动提供执行隔离，检查发生的时序也需要单独核对。

## 固定ADAS评估器先执行什么

固定`evaluate_forward_fn`先建立namespace={}，执行`exec(forward_str,globals(),namespace)`，之后检查namespace只有一个名字且对应值可调用，最后将它安装为AgentSystem.forward。第二参数是评估器的全局映射，第三参数是局部名字映射；一个空的局部字典不是一个独立进程，也没有自动撤销已发生的操作。

构造一个只操作本地列表的例子。先在评估器全局放置marker=[]，候选文本按顺序写：

```python
marker.append('before validation')
def first(self, task): return 'B'
def second(self, task): return 'B'
```

执行后namespace有first和second两个名字，所以入口数量检查会拒绝。可是marker已经变成`['before validation']`。这个列表变更发生在检查之前，拒绝入口不会把它回滚。原函数本地桩已核对这一顺序；例子不访问文件、网络或外部服务，也不声称论文生成了这种候选。

## 接口约束与能力边界各自负责什么

“仅一个名字”“可调用”“返回A/B/C/D”等约束可以帮助评估器调用候选，但没有描述其顶层语句、全局状态访问或资源使用。即使最后只导出一个函数，顶层语句也可能已经执行；反过来，两个函数可能只是接口不符合约定，并不自动说明其内容危险。

若设计目标要求先检查接口再执行，应先解析文本并验证允许的结构，不能靠执行后的namespace长度完成这个目标。静态结构检查仍不是任意Python代码的完整隔离机制；运行权限、资源预算、可访问数据及进程边界需要另行实现。若环境明确可信、允许共享状态，也应将这项假设写进协议，而不是从空字典推断它已经隔离。

## 评价记录需要关联执行环境

保存候选文本及摘要、接口检查结果、何时执行、执行环境与能力、退出原因及资源使用。候选被拒绝后，记录它是否已执行过顶层代码；失败结果与副作用不能只用一个“invalid”标签抹平。比较不同搜索系统时，若一个允许读到更多评估器状态，另一个只获得受限输入，二者的评价条件也不相同。

练习：将数量检查移到exec之后但加入try/except，是否会自动恢复marker为空？答案：不会；捕获异常与回滚先前列表变更是不同操作。本例只证明该局部状态变化，不据此声称某个操作系统边界的性质。
